### Вывод по двум запросам:  
Первое - отсутствие строгой валидации входных данных. При отправке невалидных данных сервер не отклонил запрос с кодом 4xx, а обработал его иначе [уточните: вернул 200, 500 или пустой ответ] — это признак недостаточной серверной валидации.  

Возможное отсутствие rate limiting. Если повторные невалидные запросы не блокируются — риск brute-force.  

### Рекомендации по исправлению:
Ввести схемы валидации для всех эндпоинтов.  
Унифицировать формат ошибок (например, RFC 7807 Problem Details).  
Добавить negative-тесты в CI.  
Отключить verbose-ошибки в production

### Вывод:  
Чередование успешных ответов (200 OK) и ошибок (429) указывает на то, что система балансировки или антибот-фильтр пропускает часть трафика, создавая непредсказуемую нагрузку на бэкенд.  

Анализ графика JMeter показывает, что до момента срабатывания блокировки (429) сервер испытывал трудности: медианное время отклика (красная линия) неуклонно росло. Это связано с тем, что запросы не отклонялись мгновенно, а «висели» в очереди (Connect Time достигал ~700 мс), что приводило к перегрузке пула соединений на стороне клиента.  

### Рекомендации по исправлению:  

Настроить единые правила Rate Limiting на уровне API Gateway (например, по токену авторизации или API-ключу, а не только по IP), чтобы поведение системы было предсказуемым.  

Настроить WAF/Rate Limiter так, чтобы при превышении лимита ошибка 429 возвращалась мгновенно (в первые 10–50 мс), ещё до установки полноценного соединения с бэкендом. Это освободит пул соединений и снизит нагрузку на инфраструктуру.
